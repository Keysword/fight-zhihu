## 第一部分：全面评估

### 1. 工程基线（实测）

| 维度 | 结论 | 依据 |
| --- | --- | --- |
| 规模 | 核心服务端 + 领域层约 2.2k 行（含测试） | `wc -l` |
| 测试 | 15 个文件 / 60 用例全部通过，1.68s | 实测运行 |
| 架构 | SvelteKit PWA → API（校验/脱敏/限流）→ SQLite / 受控 Agent 循环 | README、源码 |
| 安全设计 | 证据引用校验、动机归因禁令、外部线索逐字节比对、脱敏双端执行、案例不可枚举 | `agent/tools.ts`、`privacy/redact.ts` |
| 部署 | 独立用户、127.0.0.1:3210、systemd、Nginx、原子切换与回滚 | `deploy/` |
| 前端 | 组件层很薄（10 个组件，合计约 250 行），展示逻辑集中在页面 | `wc -l` |

工程质量明显高于一般比赛原型：**"Agent 只能通过受控 JSON 动作申请写入，写前校验完整结构与证据引用"**这条设计是认真的，且单测真的覆盖了安全分支。

### 2. 真正的资产（值得为它继续投入的理由）

1. **问题重定义准确**：把痛点从"职场沟通/情商"改写为"背景信息缺失"，使问题可结构化、可验证、可工具化。
2. **核心洞察不可替代**："最终审批者 ≠ 关键补全者"，且"权威性必须按子问题判断，不能按人整体判断"。这个判断来自真实卡点，不是访谈能问出来的。
3. **市场空位经调研确认**：竞品全部站在公司一侧，没有产品服务"信息不对称中的弱势个人"。
4. **可信度机制而非合规姿态**："事实/说法/推断/未知/冲突"五分法 + 外部内容不升级为事实 + 只判断信息能力不揣测动机——这三条同时是合规设计、信任设计与差异化设计。
5. **交付完整度**：P0 闭环已闭合，有线上地址、有部署脚本、有回滚路径。

### 3. 硬约束核查（代码事实，非推断）

以下是评估中新查证、且**未在现有文档中记录**的约束。它们直接影响下一步该改什么。

#### 3.1 安全校验失败是"一次死刑"，没有修复重试

`app/src/lib/server/agent/runtime.ts` 中：

- 协议错误（模型没吐出合法 JSON）有**一次**自动修复机会（`protocolRepairUsed`，第 121 行）。
- 安全校验错误（`validateBoardForCase` 抛出的 `AgentSafetyError`，第 196 行）**直接抛出**，没有任何重试。

后果：模型可能已经花掉 4–5 个决策回合构建出一份完整背景板，只因某条判断引用了案例外证据、或某个事实挂错了证据类型，整轮运行直接失败，用户什么都拿不到。这段已验证的严重路径（`runtime.test.ts:216`）只断言了"会抛错"，没有断言"能否恢复"。

#### 3.2 `fact` 被强制要求引用正式通知，而演示案例本身零事实

`agent/tools.ts` 的 `assertFactSupport`（第 28–41 行）：

- `fact` 类判断**必须**至少引用一条 `kind === 'notice'`（正式通知类）证据；
- 且判断文本与通知正文必须共享至少一个三元组。

实测：`demo-case.ts` 中 `kind: 'fact'` 出现 **0 次**，`kind: 'notice'` 出现 **0 次**。演示板的 6 条判断全部是 `unknown` / `statement` / `conflict`。

即：**产品最重要、最可信的"已确认事实"这一档，在唯一一个经过精心设计的示范案例里从未被使用过。** 说明这条规则在当前材料形态下几乎无法触发——用户手里通常只有聊天记录和口头转述，没有正式通知。规则本身有测试（`tools.test.ts:42`），方向是对的，但与真实使用形态存在结构性错位。

#### 3.3 失败原因对用户不可见

`services/case-service.ts` 的 `appendEvidenceAndRun`（第 193–208 行）用 `catch { ... }` 无差别捕获，把任何异常都变成一句"证据已经保存，但 Agent 本轮暂时没有完成判断"。`AgentSafetyError` 的具体原因既没有写进事件，也没有返回给前端。

后果：开发期无法定位模型为什么被拒；用户期只能看到笼统失败，无法自我修正材料。

#### 3.4 决策预算耗尽 = 整体失败，无部分结果

`MAX_TURNS = 6`、`MAX_SEARCHES = 2`（`runtime.ts:11–12`）。超出时抛 `AgentLimitError`，整轮失败。对于材料多、参与者多的事项，6 轮可能不够，但失败方式过于武断——理论上可以返回"当前已整理的进度"。

#### 3.5 没有沉淀层：产品价值最高的一环在类型系统里不存在

`domain/types.ts` 只有 `Evidence` / `Claim` / `Participant` / `KeyCompleter` / `NextAction` / `ExternalClue` / `BackgroundBoard` / `CaseSummary` / `CaseRecord` / `AgentEvent`。**没有任何实体承载"公司隐性规则"**。项目说明第六节"逐渐形成个人背景地图"与产品设计 5.6 之后的愿景，当前实现度约为 0。

### 4. 结构化风险清单

按"会不会让项目失败"排序，不按实现难度排序。

| # | 风险 | 严重度 | 判断依据 |
| --- | --- | --- | --- |
| R1 | 安全链 100% 拒绝、0% 修复，真实案例可用性不可预期 | **高** | 3.1 |
| R2 | `fact` 门槛脱离材料形态，最可信的一档形同虚设 | **高** | 3.2 |
| R3 | 唯一有留存价值的能力（背景地图）未实现 | **高** | 3.5 |
| R4 | 价值重心错配：最贵的证据链不是最被需要的，最需要的沉淀没做 | **高** | 见 5 |
| R5 | 留存假设未验证（用户会不会建第二张板） | **高** | 无任何真实用户数据 |

### 5. 核心判断（本方案的最重要结论）

产品同时承担三件事，而三者的**用户渴望度**与**替代难度**并不匹配：

| 层 | 内容 | 用户当下想要的程度 | 被替代难度 | 当前投入 |
| --- | --- | --- | --- | --- |
| A | 行动建议：找谁、问什么、一段可直接发的话 | 极高 | **低**（通用 AI 就能写） | 中 |
| B | 台账/证据链：事实-说法-推断-冲突 + 可回溯 | 中 | 中 | **极高** |
| C | 个人背景地图：沉淀"这家公司的隐性规则" | 高（且有复利） | **高** | **≈0** |

**最贵的那部分（B）不是用户当下最想要的；最值钱、唯一有留存的那部分（C）几乎没做。**

B 的正确定位是**信任机制**，不是**效率机制**：它让用户和评委相信结论，但不直接让人更快办成事。因此 B 不应被削弱，但应改变**呈现强度**——默认给结论与置信度，证据按需展开。

同时必须承认：真正的竞争对手不是通用 AI，而是**群里那句"你问下行政 XX"**。那个方案零录入成本、五分钟出结果。产品要赢，只能在足够窄的场景上做到 10 倍好，而不是覆盖"任何卡住的事"。

## 第二部分：方案选型

### 选项 A：决策助手路线（强化 A + 修正 B）

- 主线：把"这一步找谁、问什么、怎么说"做到无脑可用；
- B（证据链）保留为信任底座，但降低默认呈现强度；
- C 作为副产品，用最小代价落地。

**优点**：与现有实现最贴合，改动集中在运行时与提示层，风险最低；直接对准用户当下最高渴望。
**缺点**：A 层最易被通用 AI 复制，护城河仍依赖 B/C。

### 选项 B：背景地图路线（主攻 C）

- 主线：每解决一件事自动沉淀"公司隐性规则"，形成个人化的组织知识库；
- A 层作为入口与副产品。

**优点**：护城河最深、复利最强、留客理由最硬。
**缺点**：价值需要多次使用才显现，冷启动期用户感觉不到；依赖"用户愿意回来第二次"，而这恰恰是尚未验证的假设。单独作为第一优先会赌一个未验证前提。

### 选项 C：极简答案路线（只做 A）

- 砍掉台账与沉淀，只做"输入碎片 → 输出找谁/问什么/怎么说"。

**优点**：最快、最轻、留存压力最小。
**缺点**：与通用 AI 无本质区别，放弃已验证的差异化，等于否定项目最有价值的部分。**不建议。**

### 推荐：A 为主线，C 为承载，B 保持为信任底座

理由：

- A 是用户当下唯一愿意为之打开产品的理由，必须先做到无懈可击；
- C 是唯一能形成留存与护城河的能力，必须**在本轮就落地最小版本**，否则永远停在 P1；
- B 已经建好且质量不错，是差异化叙事与评委说服力的来源，**保留但不加重**；
- 顺序上先修 R1/R2/R9（可用性），再建 C（留存），最后才是入口收窄与验证。

## 第三部分：唯一必须最先做的验证（不写代码）

在投入任何新功能之前，用约一周时间做一次盲测：

- 对象：10 位职场新人，每人给**一件当下真实卡住的事**（不接受编造场景）；
- 方法：同一份材料分别交给背景板与通用 AI，输出顺序打乱后盲评；
- 必答三问：
  1. 看完之后，能不能说出"下一步找谁、问什么"？
  2. 这张板是帮上忙了，还是挡路了？
  3. 你还会不会为下一件事再建一张板？（**生死题**）
- 行为指标：生成的求助消息实际发出去了吗？对方回复了吗？事情推进了吗？

**判定规则**：

- 若第 3 问多数为"不会"→ C 层设计需要重做（改为"自动沉淀、零维护"形态），甚至重估整条路线；
- 若第 1 问通过率低于通用 AI → A 层是当前最大短板，优先修 A；
- 若第 1 问显著高于通用 AI、但第 2 问抱怨流程重 → 问题在录入与审阅成本，按下面阶段 2 处理。

在这次验证完成前，**不建议继续增加功能**。

## 第四部分：分阶段改进计划

### 阶段 1（优先）：修正决策链路，让"跑到一半失败"变成"可修复"

目标：现实材料也能稳定产出可用的板。对应 R1 / R2 / R9 / R11。

1. **给安全校验失败一次修复机会**
   - 在 `runtime.ts` 中新增 `safetyRepairUsed`，与 `protocolRepairUsed` 对称；
   - 捕获 `AgentSafetyError` 后，把**具体拒绝原因**作为工具消息回灌模型，要求只修正被拒字段后重新提交；
   - 第二次仍失败才抛出，并记录 `agent.error`（`category: 'safety'`）。
2. **失败原因可见化**
   - `AgentSafetyError` / `AgentLimitError` 增加结构化 `code`；
   - `case-service.ts` 的 `catch` 保留原始原因，写入事件并在 API 响应中返回 `reason`；
   - 前端在失败态展示可理解的下一步建议（例如"某条判断缺少证据支撑，可补充材料或重新分析"）。
3. **放宽 `fact` 的支撑来源（保留严格性，去掉单一形态依赖）**
   - 维持 `fact` 必须引用证据；
   - 将"必须引用 `notice`"调整为"必须引用 `notice`，或引用用户显式标记为**已确认**的证据"；
   - 为 `Evidence` 增加可选 `confirmation` 字段（`self_reported` / `official`，默认 `self_reported`），前端在录入时提供"这条是正式通知吗"的选择；
   - 三元组支撑校验继续保留，防止"挂错证据"。
4. **决策预算耗尽返回部分结果**
   - 达到 `MAX_TURNS` 时，若已有可校验的板，返回 `outcome: 'partial'` 并明确告知"本轮未完成，但当前进度可用"；否则才失败。
5. **补测试**：安全错误一次修复成功、修复后仍失败、`fact` 两种支撑来源、预算耗尽返回部分结果。

**验收**：阶段 1 完成的标志是——用 3 个真实（脱敏）案例跑通分析，不再出现"整轮失败且用户不知道为什么"。

### 阶段 2：落地最小可用的"个人背景地图"（C 层）

目标：把唯一有留存价值的能力做出来，且做到**零维护**。对应 R3 / R4。

1. **数据模型**（`domain/types.ts` 新增）
   - `BackgroundRule { id, caseId, scope, rule, basis, confidence, createdAt, supersededBy? }`
   - `scope`：职责 / 流程 / 渠道 / 联系人 / 时效限制；
   - `basis`：这条规则是从哪次办事、哪条证据得来的（可回溯）；
   - `supersededBy`：允许后续事项修正旧规则，而不是简单覆盖。
2. **自动沉淀**
   - 每次案例进入 `actionable` 或 `resolved` 时，让 Agent 额外输出 `backgroundRules`（3–5 条），经与背景板相同的校验后落库；
   - 抽取原则：只沉淀**可复用的组织事实**（"住宿分配实际由物业执行，人力只发通知"），不沉淀一次性细节（"房间号 302"）。
3. **去重与冲突**
   - 同 `scope` 下语义重复的规则合并；
   - 新旧规则冲突时保留两条，标记后者"依据更近"，不静默覆盖。
4. **界面**：`背景地图` 页，按 scope 分组展示，每条可展开看来源案例。
5. **反哺闭环（关键）**：新案例分析时，把相关历史规则作为**"我自己的历史经验"**注入提示上下文。注意：历史规则只能作为待验证线索，不得直接升格为新案例的事实，与外部线索同等对待。

**验收**：连续办理三件同类事项后，第三件的板能引用前两件沉淀的规则，且用户可以不阅读规则库也不影响办事。

### 阶段 3：收窄入口，把"任何事"变成"最擅长的那类事"

目标：解决 R6。对应产品设计 3.2。

1. **主打场景**：**"入职第一周卡住的事"**（门禁、工位、系统权限、报销、社保公积金）。
   - 高频、新人必然遇到、不涉及敏感业务信息、正是背景地图最容易起作用的阶段。
2. **事项模板**
   - 为高频事项提供模板（目标、常见参与者角色、常见必需信息、常见前置条件）；
   - 模板只做**起点预填与追问引导**，不改变"Agent 无固定工作流"的架构原则。
3. **案例标签**
   - 为每张板增加 `scenario` 标签，用于背景地图的 scope 归类与检索。
4. 宿舍案例继续作为标杆演示案例；户口迁移作为通用性验证案例。

### 阶段 4：判断表述与证据分级校准

目标：解决 R7，并进一步降低幻觉与误伤风险。

1. **引入证据来源分级**
   - 为结论标注 `basisKind: 'case_material' | 'general_practice'`；
   - `general_practice` 类判断在界面上**视觉降级**，并显式说明"这是常见做法推断，需要向本单位确认"；
   - 这样可以保留"关键补全者"判断的价值，同时不让常识先验伪装成证据。
2. **表述校准**
   - 把"X 是权威方"统一改为"最值得先问 X，理由是……"，强化产品是**问题生成器**而非**组织推断器**的定位。
3. **反哺闭环的护栏**：历史规则与外部线索一律不得进入 `fact`。

### 阶段 5：防外传护栏与工程债

对应 R8 / R10 / R12 / R13。

1. **防外传**
   - 生成的求助消息中永不出现"我做了个分析/AI 告诉我"等元信息；
   - 参与者与补全者判断默认仅本机可见，不随消息导出。
2. **知乎定位调整**：明确作为"帮你发现没想到要问的问题"的补充，不做关键路径；文案与演示脚本同步降低其权重。
3. **工程债清单**
   - 模型输出评测脚手架（产品设计 12.2 要求的人工标注与指标计算，当前没有）；
   - 安全规则细化（`INTENT_LANGUAGE` 正则较宽，误伤与漏判都需评估）；
   - 账号与访问控制（`CaseSummary` 无 owner 概念，当前总列表不公开是靠设计约束而非权限）；
   - preview 与 production 的 SQLite 目录必须严格隔离；
   - 案例删除与数据保留期限。

### 明确的非目标（本轮不做）

- 不做企业知识库、组织通讯录或任何需要公司接入的能力；
- 不做多人协作、公开分享、权限系统；
- 不自动替用户发送消息；
- 不做领导性格、同事人格、办公室政治分析；
