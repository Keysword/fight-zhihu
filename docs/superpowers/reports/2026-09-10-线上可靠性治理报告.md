## 一、这份报告回答什么

上一轮评估给出了"阶段 1：修正决策链路"的计划。本报告记录该计划落地到生产的全过程，重点是**用真实模型实测发现的、仅靠读代码和跑单测看不到的问题**。

核心结论一句话：

> 背景板的板逻辑没有坏，**坏在模型输出进入板逻辑之前的那几层**——解析、诊断、schema 容错、以及一条过严的证据规则。这些问题只有在真实模型上才会暴露。

## 三、问题清单（按发现的先后）

所有问题都是**部署后在真实模型上实测**发现的，不是读代码推测的。

### P1 安全校验失败是一次死刑

- **现象**：模型花 4–5 轮构建的板，因一条判断引用的证据不合规，整轮失败，用户什么都拿不到。
- **定位**：`runtime.ts` 给协议错误一次自动修复机会（`protocolRepairUsed`），但 `AgentSafetyError` 直接抛出。
- **修复**：新增 `safetyRepairUsed`，与协议修复对称；把**具体拒绝原因**回灌模型。
- **实测验证**：事件流出现 `agent.safety_repair`，reason 精确命中规则。

### P2 失败原因全丢

- **现象**：旧版遇到安全校验失败返回笼统 502，事件流里**只有 `agent.action`，没有任何 error 事件**，系统日志也已轮转。
- **修复**：新增 `runErrorDetail()` 产出 `title/summary/suggestion`；`case-service.ts` 保留原因并写入 `agent.run_failed`；`apiError` 返回结构化字段。
- **顺带**：`APP_VERSION` 是 `.env` 里写死的 `0.1.0`，`deploy.sh` 从不更新，导致 `/api/health` **永远无法区分发布版本**。已改为部署时写入 release id。

### P3 `fact` 规则与真实材料形态错配

- **现象**：只有聊天记录（最普遍的真实形态）的案例**直接 502**。
- **对照实验**：同一场景加一条 `notice` 证据即成功。**只改了证据类型**。
- **修复**：`Evidence` 新增 `confirmation: 'official' | 'self_reported'`；`fact` 可引用正式通知**或用户已确认的证据**。

### P4 错误分类错误（阶段 1 引入的回归）

- **现象**：协议错误（模型没返回合法 JSON）被报成"**未通过安全校验**"，把用户引向错误的补救方向；title 也是通用的"本轮分析没有完成"。
- **修复**：协议/安全/超时各有独立 title、code、suggestion。

### P5 nginx 超时腰斩修复回合

- **现象**：安全修复要多跑一轮模型调用，一次运行达到 92 秒，撞上 `proxy_read_timeout 90s`，变成 504。
- **修复**：90s → 180s → **300s**（见第六节，这是安全网不是目标）。

### P6 解析器把合法 JSON 判为非法 ⭐

**这是最具决定性的一次诊断，也推翻了我自己的一个判断。**

我原本建议"切到支持 JSON mode 的端点"。**实测证明这个判断是错的。**

用产品真实 prompt 探测模型 3 次：

```
run 1: JSON_EMBEDDED_IN_PROSE   ← 输出以 "{" 开头，含完整合法动作对象，只是后面跟了话
run 2: PURE_JSON
run 3: JSON_EMBEDDED_IN_PROSE
```

旧 `extractJson` 要求"以 `{` 开头**且**以 `}` 结尾，否则必须是一个完整代码块"，因此把已经合法的动作拒了。

**修复**：改为扫描**第一个平衡的 JSON 对象**，跟踪字符串状态与转义（避免字符串内的花括号被当边界）。

**效果**：线上口径失败率从 0/1 变为 1/3。

### P7 错误信息不可诊断

- **现象**：只说"模型动作不符合协议"，不给字段。模型无法据此修正，人无法据此定位。
- **修复**：带上 Zod issue 路径，例如：
  ```
  board.claims.4.evidenceIds: Invalid input: expected array, received undefined
  summary: Invalid input: expected string, received undefined
  ```

### P8 schema 过度严格（由 P7 直接定位）

- **现象**：模型对 `unknown` 类判断省略 `evidenceIds`（语义上确实不需要证据），却导致整轮失败；`summary` 也常漏写。
- **修复**：`evidenceIds` 默认 `[]`，`summary` 默认固定文案。
- **关键约束**：`fact`/`statement` 的证据底线**没有被放松**——由 `superRefine` 继续把守，有测试覆盖。

### P9 模型改不动时用户仍然拿不到结果 ⭐

- **现象**：安全修复回灌原因后，模型**经常第二次仍然把信息标成 `fact`**，于是整轮失败。这是降级兜底前的主要残留失败。
- **修复**：第二次仍失败时**由产品兜底**——`downgradeUnsupportedFacts` 把无充分证据的 `fact` 改写为 `statement`，保留文本，在 `rationale` 写明"缺少正式确认，暂按他人说法记录"，再复检；只有降级后仍不合法才真正失败。
- **设计要点**：校验与降级**共用同一断言函数**（`factSupportProblem`），避免两处规则漂移。

### P10 确认动作藏在角落（交互）

- **现象**：只有一个不起眼的小勾选框，用户难以发现"证据可以被确认"，而这条规则是 `fact` 能否成立的前提。
- **修复**：证据轨上每条未确认证据增加虚线按钮「**负责方已明确回复过**」，确认后显示绿色「已确认」徽标；新增 `POST /api/cases/:id/evidence/:evidenceId/confirm`；轨上方加说明。确认**不触发重新分析**。

## 四、阶段性成果

### 4.1 成功率

同一案例、同一材料，连跑 3 次：

| 阶段       | 成功    | 失败原因         |
| ---------- | ------- | ---------------- |
| 治理前     | 1/3     | 安全规则拒绝     |
| **治理后** | **2/3** | 1 次超时（181s） |

> 样本量小（3 次），仅作为方向性指标，不构成统计结论。

### 4.2 兜底降级的线上实录

```
agent.action          propose_board_patch（模型标为 fact）
agent.safety_repair   背景板未通过安全校验，已要求模型修正
agent.action          模型自行降级为 statement
agent.error           模型连续两次未通过安全校验
agent.fact_downgraded 2 条缺少正式确认的判断已按他人说法记录   ← 系统兜底
tool.result
agent.finished        outcome: finished                          ← 用户拿到结果
```

模型的文本、参与者、关键补全者、下一步行动**全部保留**，只有确定性档位被降级。

### 4.3 存量数据安全性（部署前验证）

生产库中有 **5 条 `fact` 判断引用的是 `message` 证据**，按新规则不合规。部署前逐项核对：

- 它们只在**待审确认**时才会被复检，而线上待审提案为 **0**，因此当前惰性、不会报错；
- 专门新增 `fallback-validation.test.ts` 覆盖 README 推荐的完整演示闭环（含物业回复后转为 `actionable`），**新代码通过**，演示路径不受影响。

### 4.4 迁移演练

用生产库副本（12 案例 / 50 证据）在本地跑新代码迁移：`confirmation` 列正确新增，**NULL 行数为 0**，历史 `notice` 回填为 `official`。

## 六、仍未解决

按影响排序，**不粉饰**。

1. **单轮耗时 40–90 秒，单次运行可达 181 秒。** 300s 超时只是安全网，不是目标。用户等 3 分钟不可接受。**这是当前第一体验硬伤。** 真正的解法是减少轮次或缩短单轮输出，尚未动。
2. **模型输出仍有约 1/3 抖动。** 降级兜底解决了"事实规则"这一类，但协议错误（模型臆造动作名）和超时仍在。
3. **模型倾向把"已确认信息"写成 `fact`。** 兜底能接住，但用户看到的是"他人说法"而非"事实"，信息档位被系统性压低。
4. **`partial` + 已 staged 提案分支不可达**（阶段 1 分析结论），语义已简化但未删除。
5. **搜索预算超限仍是硬失败**（阶段 1.5 遗留项）。
6. **背景地图（C 层）仍为 0 实现**，且按修订后的计划被**门禁卡住**：需先解决归属与隔离，并等 M0 显示真实复用需求。
7. **M0 十案例盲测尚未开始。** 在成功率只有 2/3 的基础上跑，测出来的主要是模型抖动而非产品价值。

## 八、方法论备注

本次治理中，**每一次修复都立即部署到生产并用真实模型复测**。结果是：几乎每一轮都暴露出下一层问题（P6 → P7 → P8 → P9 是一条完整的链），而这些问题在单元测试和代码阅读中都不出现。

因此本报告的一条经验是：**对这类 agent 产品，单测通过 ≠ 能用；必须用真实模型在生产口径上跑。**

代价也要说明：本轮在生产库中创建过若干测试案例，均已通过 Node 内置 SQLite 精确删除，生产库已恢复为 12 条原创案例，无残留。

## 九、勘误（2026-09-11 追加）

原文保留不改，以下为后续复核发现的错漏。

### 9.1 成功次数需要写全，且样本范围要限定

第四节"成功率"表格中的 `1/3` 与 `2/3`，完整表述是：**同一个案例、同一份材料，连续运行 3 次**，治理前 1 次成功、治理后 2 次成功。

这两组数字都是**单案例的 3 次运行**，不是跨案例的样本，因此：

- 不能读作产品的总体成功率；
- 第六节第 2 条"模型输出仍有约 1/3 抖动"同样只是那 3 次运行的观察，**不是**一般失败率或尾部延迟结论；
- 后续若要给出失败率，需要固定模型、材料与判定标准，逐次记录并保留失败样本，样本量也要足够。

### 9.2 `partial` + 待审提案分支是可达的（原文结论错误）

原文第三节 P9 之后的附带结论、以及"六、仍未解决"第 4 条称：

> `partial` + 已 staged 提案分支在当前控制流下**不可达**……删除兜底后此分支语义变简单。

**该结论错误。** 复核实测：对已有正式背景板的案例，让模型连续提交 6 次合法的 `propose_board_patch`，即可在轮数上限处返回 `outcome: partial`，且 `proposedBoard` 与持久化的 `pendingBoard` 同时存在。

当初得出"不可达"是因为测试脚本用了 `search`（先撞搜索上限抛错）或 `finish`（提前返回），没有尝试"连续提交板"这条路径。

因此：

- 该分支**不能被当作死代码删除**；
- 移除 `?? caseRecord.board` 兜底这个**修改本身仍然正确**（作用是防止把已生效的板当成待审提案返回给前端），但删除的**理由不成立**；
- 现已补三条边界测试：真实待审提案会被交回；没有新提案时绝不把旧板当提案；首次建板且无待审提案时返回 `partial` 但不带提案。

### 9.3 `response_format` 需要显式实现

原文第七节写"填上三个 `AGENT_*` 变量……且可直接使用 `response_format`"，表述容易误解。

实际情况：`app/src/lib/server/agent/model-client.ts` 的请求体是

```ts
body: JSON.stringify({ model: configuration.model, messages, stream: false });
```

**没有传 `response_format`。** 因此：

- 三个 `AGENT_*` 变量**只切换调用路径**（绕过 OpenCode，改走 OpenAI 兼容端点），**不会**自动启用 JSON mode；
- 将来若要用 JSON mode，需要先验证目标端点确实支持该参数，再在客户端显式实现并补契约测试；
- 这也意味着 P6（解析器过严）当时**不能**靠"切端点"解决，必须改解析器——切端点解决不了"输出后带解释"这类问题。

### 9.4 两条证据不能单独推出"聊天记录都应升为事实"

原文 P3 引用了两项证据，各自能证明的范围有限：

| 证据                                                        | 它实际证明的                                                       | 它不能证明的                                                 |
| ----------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------ |
| 生产库 50 条证据中 `notice` 为 0 条（38 message + 12 note） | 该库中证据**来源分布**以聊天与笔记为主，正式通知类证据没有被使用过 | 不能证明所有聊天记录都应当被当作事实                         |
| 对照实验：同一场景仅改变证据类型（加一条 `notice`）即成功   | 旧规则确实会因为缺少 `notice` 而拒绝一份本来可用的板               | 不能证明放宽到"用户已确认的聊天记录"之后，所有此类判断都成立 |

正确的结论是：**旧规则的证据形态假设与真实材料不匹配**，因此需要放宽来源并要求用户确认；而不是"聊天记录天然等于事实"。放宽后仍必须保留内容支持校验（原文没说的内容不许写成事实），这一层在 2026-09-11 的修复中才真正补上。
