## 1. 结果判断

本轮已经完成可本地运行、可回退、可重复验证的引导式帮助闭环。新路径不再要求程序判断模型的一段自然语言是否是“正确事实”，而是让模型交付一版可以被纠正的工作理解、零到两个引用本案例材料或用户输入的沟通疑点，以及一个值得尝试的下一步。

用户反馈已经成为一等输入。用户可以直接说明“理解有误”“联系不上”“我问过了”或“有新回复”；应用先保存反馈，再开始新一轮整理。分析失败不会吞掉输入，较晚返回的旧分析也不能覆盖新上下文。

工程闭环完成不代表产品帮助效果已经成立。当前环境没有 `AGENT_*`、OpenCode Server 或知乎直答模型配置，因此没有生成 20 份真实模型输出，也没有进行五维人工评分。脚本模型的 11 个浏览器测试只证明数据、交互和失败恢复合同可以工作，不能证明真实模型会给出有启发、合适且不误导的建议。

## 2. 已实现的产品行为

### 新的输出形态

- “当前理解”明确是一版可修正的工作理解，可包含一个尚未弄清的关键点。
- “值得核对的沟通疑点”最多两项；每项在结构上必须引用本案例材料或用户输入。程序不判断引用在语义上是否足以支持疑点，其合理性由模型提示、用户纠正和真实产品评测检验。
- 沟通提醒描述观察、可能误读、行动影响与核实办法，不给人物打可信度分。
- “可以先试这一步”只保留一个动作，可附消息草稿和最多两个答复分支。
- 一般角色建议固定标明“可尝试的入口，尚未确认本单位职责”。
- 外部引用固定标明“外部经验 · 仅供启发”。

### 反馈与历史

- 原材料、用户反馈和模型指导分别存储，模型不能改写前两类内容。
- 输入接口按 `requestId` 幂等；同一个请求标识携带不同的脱敏规范化内容会明确冲突。
- 用户输入、新材料与材料确认会增加独立的 `context_revision`，不与旧背景板修订号混用。
- 指导按上下文版本写入。旧版本晚返回时只可留作历史，不能成为当前指导。
- 当前指导、变化说明、用户输入和最近 20 次指导摘要可在刷新后恢复；完整历史按案例和指导 ID 单独读取。
- 输入比当前指导更新时，页面显示“这是补充前的理解”。

### 失败、并发与预算

- 单案例使用进程内 single-flight；同一版本复用请求，新版本排在旧运行之后，不同案例可以并行。
- 每轮最多 5 次模型调用、2 次搜索、1 次结构或引用修复。
- 超出搜索额度后要求模型利用已有材料继续指导或追问，不直接让整轮失败。
- 首个合法 `provide_guidance` 会立即保存并结束，不再额外调用 finish。
- runtime 正常进入 execute 后的受控结果通过统一结束事件记录运行 ID、结果、总耗时、模型调用次数与各次耗时、搜索次数、修复次数及失败码；不记录完整提示或模型原始回复。

### 模式切换与旧数据

- `BACKGROUND_BOARD_GUIDANCE_V2=1` 成套切换首页、新建页、案例页、运行入口和匿名演示。
- 开关关闭时继续使用原背景板页面和旧 Agent 路径；引导专用 API 返回未启用。
- 同一 SQLite 数据库在旧模式、引导模式、再回到旧模式后，旧背景板、旧待审提案、新反馈和新指导快照都保留。
- 关闭开关不会删除新增表，也不会覆盖旧 `board_json` 或 `pending_board_json`。

## 4. 工程验证

2026-09-13 在本地工作区重新执行：

| 检查 | 结果 |
| --- | --- |
| `pnpm format:check` | 通过 |
| `pnpm lint` | 通过 |
| `pnpm check` | 通过，0 error / 0 warning |
| `pnpm exec vitest run` | 25 个文件、182 项通过 |
| `pnpm exec playwright test` | 11 项通过，约 34.2 秒 |
| `pnpm build` | 通过，adapter-node 产物生成 |

浏览器测试由三个本地进程组成：关闭开关的旧模式、开启开关的引导模式、只监听 loopback 的脚本模型。单次全局启动创建一个带随机所有权标记的临时根目录，两套应用在其中使用不同的 SQLite 子目录。清理前校验目录类型、规范化父目录、完整名称和所有权标记；实跑前后的测试目录清单一致。真实模型、OpenCode 和知乎凭据被显式清空。

覆盖的关键旅程：

1. 输入材料，得到一版理解和一个下一步；
2. 报告“联系不上”和“我问过了”，下一版不重复旧建议；
3. 刷新后指导、脱敏反馈和历史仍在；
4. 模型先追问，用户回答关联到对应指导，再生成下一步；
5. 模型一次失败后输入仍在，只重试整理且输入不重复；
6. 旧请求延迟返回时，切换后的案例、指导和未提交草稿不会串案；
7. 修改新建内容、反馈或追加材料后，原脱敏确认立即失效；
8. 关闭开关时旧匿名演示、旧待审板和旧页面继续工作。

脚本模型的有效指导均在一次模型调用后结束，事件记录的 `modelCallCount` 为 1、`searchCount` 为 0。这只验证“不需要额外 finish 调用”的工程性质。

## 5. 产品评测准备与未完成项

[固定场景数据](../../../app/evals/guidance/cases.json) 已包含 10 个案例，每个案例都有目标、材料、用户限制、后续反馈、应关注点和必须避免的误导。场景包括：

1. 把宿舍申请承诺误当成结果；
2. 房间和钥匙已经明确，不应制造疑点；
3. 接引联系人不能确认住宿；
4. 两次转述丢失审批条件；
5. 去年报销经验不等于当前退单原因；
6. 没有联系方式时不能重复建议直接联系；
7. 用户已经问过后必须改变下一步；
8. 用户纠正角色判断；
9. 材料模糊时先给有价值的追问；
10. 理解用户抱怨，但不替用户生成指控。

真实模型评测本轮为 **0/20 次指导**，五维人工评分为空，严重误导记录为空。这表示“尚未评”，不能解释为零误导。下列门槛尚未验证：

- 10 个场景中没有严重误导；
- 至少 8/10 首轮给出可执行帮助或有价值追问；
- 预设不可行反馈后至少 8/10 实质调整；
- “安排已经明确”的对照场景能够收起疑点；
- 真实调用次数、失败、超时和耗时相对旧路径是否改善。

## 6. 审查中发现并修正的问题

- 同一案例在运行期间收到新输入时，最初实现只返回旧结果；现已自动串行处理最新版本。
- 重复确认同一材料曾错误增加上下文版本；现已保持幂等。
- 指导来源曾只在运行时校验；现已在持久化边界再次校验案例归属和外部 ID 唯一性。
- 引导 API 曾可在开关关闭时调用；现已在服务和路由层隔离。
- 历史曾一次加载全部完整快照；现只返回 20 个摘要并按需读取详情。
- 界面曾可能在客户端切换案例时保留上一案例指导、草稿或晚返回响应；现按案例重建反馈组件，并在每次异步写状态前检查请求归属。
- 修改脱敏内容后，旧确认曾保持有效；现以原始内容、替换规则和上下文组成确认签名，三条输入路径都会自动失效。
- 外部经验曾与案例材料视觉相同；现明确标注仅供启发。
- `superseded` 曾被写成仍在后台整理；现如实提示该版未成为当前理解并提供重试。
- Playwright 配置求值曾创建多余临时目录，清理边界也可能误收外部路径；现由单次全局启动独占一个带随机标记的根目录，并在正常或失败退出时精确清理。
- 跨模式测试曾在同一数据库连接上切换服务；现改为旧模式写入并关闭、引导模式重开写入并关闭、旧模式再次重开读取，覆盖初始化和重连。
- 提示中唯一完整示例曾可能让模型照例生成沟通疑点；现先给出“安排已明确、疑点为空、直接核对行动条件”的完整对照，再给有材料支持疑点的示例，并明确禁止为填合同而制造疑点。

## 7. 风险与边界

- 最大未决风险是真实模型能否稳定产出有用且克制的指导，以及两类对照示例能否抑制无依据的疑点。结构测试不能回答这个问题。
- runner 在 runtime 观测边界外意外 reject 时，服务会保留输入并返回可重试失败，但该次失败没有完整的运行事件和耗时指标。
- 运行仍随一个 HTTP 请求完成，没有持久任务队列；请求中断后的恢复只依赖已保存输入和用户重试。
- single-flight 只覆盖单 Node 进程；多实例部署仍要增加分布式锁或任务协调。
- 当前没有账号、案例删除、数据导出或跨设备同步；案例 UUID 仍是能力链接。
- 旧事实认证与背景板规则仍保留在旧模式中。它们不会进入新 Guidance 路径，但开关关闭时用户仍会看到旧产品语义。
- 固定场景尚未形成长期的真实模型结果档案；模型、版本、提示变更与人工评分需要在下一轮开始留痕。

## 8. 部署与回退

本轮没有修改线上服务、systemd、Nginx 或生产 Secret，也没有执行部署脚本。

未来小流量启用时，在服务端环境中设置：

```text
BACKGROUND_BOARD_GUIDANCE_V2=1
```

回退时移除该变量或设为非 `1`，然后重启应用。旧页面和旧运行路径会恢复；新反馈、指导快照与旧背景板数据都保留。数据库迁移是向前兼容的，不需要删除新表或还原 SQLite 文件。

## 9. 下一位 Agent 的行动

下一步只做真实模型产品评测，不继续添加自然语言裁判规则。

1. 在隔离环境配置一个准备实际使用的模型，记录模型名称、版本、采样参数、代码提交和提示版本。
2. 对 10 个固定场景各运行首次指导，再提交预设反馈并运行第二次，共至少 20 次。
3. 保存两轮原始 Guidance 输出、运行结果、调用次数、搜索次数、修复次数、总耗时、失败或超时；不要保存未脱敏的私人材料。
4. 由人按梳理、启发、沟通判断、可执行性、反馈适应五项分别给 0–2 分，并单独记录严重误导。
5. 逐个检查第二轮是否解释变化并避开已经失败的建议，尤其关注“联系不上”“已经问过”和用户纠正角色三个场景。
6. 若输出不理想，基于具体失败调整提示或交互，再重跑受影响场景；不要增加否定词表、角色词表或语义置信度阈值。
7. 达到门槛后再决定是否默认启用或部署；未达到时保持服务端开关关闭。
