# 背景板产品形态设计

> 日期：2026-09-05  
> 状态：待用户审阅  
> 产品形态：移动端优先、桌面端自适应的 Web App / PWA  
> 核心表达：一件事一张板，把零散信息变成背景判断和下一步行动。

## 1. 背景与目标

“背景板”服务刚进入职场、对组织规则和人员关系缺少了解的新人。当用户遇到一件“不知道该找谁、不同人说法不一、事情无法继续”的实际问题时，产品将聊天、邮件、通知和用户描述整理成可追溯的事项背景，帮助用户：

1. 分清已确认事实、他人说法、AI 推断、未知和冲突；
2. 找出当前真正缺失的信息；
3. 按子问题判断权威方与最可能补全信息的人；
4. 带着完整背景和明确困惑发起一次有效求助；
5. 根据新回复持续更新事项状态，直到问题能够继续推进。

第一版的目标不是让用户一次性了解整家公司，而是帮助用户解决一件具体事情。个人公司背景地图是办事过程中自动沉淀的副产品。

## 2. 产品形态决策

第一版采用可公开访问的响应式 Web App，并具备 PWA 安装能力。

选择这一形态的原因：

- 评委点击链接即可体验，无需安装、注册或配置企业环境；
- 手机适合导入聊天截图和即时求助，桌面适合查看完整背景结构；
- 同一套代码可以覆盖比赛演示和早期真实用户测试；
- 后续可以封装为原生应用，而第一版无需承担应用商店和多端开发成本；
- Web 后端可以安全代理模型和知乎开放平台请求，避免在客户端暴露凭据。

第一版不采用以下形态：

- 纯聊天机器人：无法清楚表现持续状态、证据链和关键补全者判断，容易被视为通用 AI 套壳；
- 原生手机应用：安装和分发成本高，不利于评委快速体验；
- 浏览器插件或办公软件机器人：依赖特定平台，且与“无需公司接入的个人工具”定位冲突。

## 3. 两类使用入口

### 3.1 评委体验入口

首页提供“体验新人入住宿舍案例”。该入口无需登录，加载匿名化预置材料，并引导评委在三分钟内体验完整闭环：

```text
进入案例
→ 查看零散材料
→ 生成背景板
→ 找到关键未知
→ 查看关键补全者及判断依据
→ 复制求助信息
→ 加入一条模拟回复
→ 查看事项状态更新
```

评委体验必须使用与真实分析相同的产品界面和数据结构，不能仅播放预录动画。为保证现场稳定，预置案例允许使用缓存好的结构化分析结果；用户主动点击“重新分析”时才调用在线模型。

### 3.2 真实用户入口

首页主按钮为“新建一件卡住的事”。用户不需要先建立组织架构，也不需要完成新手问卷，只需提供：

- 想完成的事情；
- 当前最困惑的问题；
- 已有材料，可粘贴文本或上传图片；
- 可选的时间要求。

产品默认创建一张仅保存在当前设备上的背景板。登录、云同步、多人协作和公开分享不属于第一版范围。

## 4. 信息架构与核心页面

### 4.1 首页

首页需要在十秒内回答三个问题：

- 产品为谁服务：刚进入职场、被一件事情卡住的人；
- 产品做什么：还原背景、找到关键补全者、组织下一次求助；
- 如何开始：新建事项或体验宿舍案例。

首页不展示复杂功能导航。主要内容只有价值说明、两个入口和隐私承诺。

### 4.2 材料输入页

输入页采用分步方式，而不是空白聊天框：

1. 你想办成什么；
2. 你现在卡在哪里；
3. 加入聊天、邮件、通知或其他材料；
4. 预览将要发送给在线服务的脱敏内容；
5. 确认并生成背景板。

产品形态需要最终支持直接粘贴文本和上传常见图片格式，图片材料先提取文字并允许用户修正。比赛版本优先保证文本输入的完整闭环；图片上传与文字提取属于时间允许时再加入的增强能力。语音文件、邮箱自动导入、微信自动读取和办公软件连接不进入第一版。

### 4.3 背景板页

背景板是产品主界面，不以聊天记录为主体。

桌面端采用三栏结构：

| 左栏：信息碎片 | 中栏：背景判断 | 右栏：下一步行动 |
| --- | --- | --- |
| 原始材料、来源、时间 | 目标、时间线、人物、说法、冲突、未知 | 关键补全者、判断依据、求助信息、外部线索 |

移动端将三栏按任务优先级改为纵向卡片：

1. 当前目标与阻塞；
2. 下一步行动；
3. 关键补全者；
4. 事实、说法和冲突；
5. 时间线与原始证据；
6. 别人走过的路。

用户打开背景板时，首屏必须先看到“现在缺什么”和“下一步做什么”，而不是先阅读完整分析报告。

### 4.4 更新结果

用户得到新回复后，可以粘贴文字或上传截图。系统必须展示本次更新带来的变化：

- 新确认了什么；
- 哪项说法被修正；
- 哪个冲突被消除或新增；
- 当前阻塞是否改变；
- 下一步行动是否需要更换。

用户确认变化后才写入当前背景板，避免模型误读覆盖既有事实。

## 5. 背景板的核心组件

### 5.1 事项状态卡

展示目标、当前状态、截止时间、关键阻塞和完成度。完成度不使用虚假的百分比，而采用明确阶段：

```text
材料不足 → 背景已整理 → 等待确认 → 可以行动 → 已解决
```

### 5.2 说法与证据卡

每条内容都必须属于以下一种状态：

- 已确认事实：有明确、可追溯的权威来源；
- 他人说法：某人在特定时间给出的陈述；
- AI 推断：模型根据材料形成的判断；
- 未知：完成事项仍然缺少的信息；
- 冲突：两条或多条不能同时成立的说法。

每条内容可以展开查看原始材料、说话者和时间。AI 不得把自己的归纳显示为已确认事实。

### 5.3 参与者卡

参与者卡展示：

- 人物或部门；
- 在当前事项中的角色；
- 已经提供的信息；
- 可能拥有的信息访问能力；
- 能否决定某个子问题；
- 能否联系上下游或协调补全信息。

角色按具体事项判断，不建立对人物的永久性人格标签。

### 5.4 关键补全者卡

这是第一版最重要的差异化组件。它必须回答：

- 当前最值得向谁求助；
- 他最可能补全哪条信息；
- 判断依据是什么；
- 判断置信度是多少；
- 他是否拥有最终决定权；
- 哪些部分仍然不能确定。

界面使用“最可能帮助补全信息”而不是“明明知道却不告诉你”。产品只判断能力和信息位置，不推断对方故意隐瞒、推卸责任或拒绝帮助。

当一件事不存在单一关键补全者时，产品按子问题列出一位主补全者和若干局部补全者，不强行选出一个“全知的人”。

### 5.5 下一步行动卡

每次只突出一个当前行动，并展示：

- 联系对象；
- 需要确认的关键问题；
- 为什么现在找他；
- 可复制的询问文本；
- 得到不同答复后的后续分支。

询问文本采用“背景和目标—已有信息—具体困惑—求助理由—明确请求”结构。用户可以编辑和复制，但第一版不替用户自动发送。

### 5.6 别人走过的路

该模块调用知乎开放平台获取相似经历，用于发现遗漏问题、隐藏条件和可能风险。每条结果展示：

- 标题、摘要和原始链接；
- 作者和发布时间；
- 与当前事项相似的部分；
- 可以借鉴的追问；
- “外部经验，仅供核实”的状态标识。

知乎内容永远不能自动进入“已确认事实”。流程类内容超过一年时显示“可能已变化”。第一版由用户主动点击“寻找相似经历”触发搜索，不在后台自动消耗接口额度。

## 6. 核心数据对象

系统使用结构化对象维护事项，避免所有状态只存在于聊天上下文中：

- `Case`：目标、当前阻塞、阶段、时间要求；
- `Evidence`：原始材料、类型、来源、时间、脱敏版本；
- `Participant`：人物或部门、角色、信息能力、判断依据；
- `Claim`：内容、状态、来源证据、相关子问题；
- `Question`：尚未解决的子问题、权威方、关键补全者；
- `Action`：当前联系对象、询问文本、答复分支；
- `ExternalClue`：知乎或官方来源、发布时间、适用性和风险提示；
- `Revision`：每次加入新材料后发生的状态变化。

这些对象相互引用唯一标识。任何结论必须能够回到具体证据或明确标记为 AI 推断。

## 7. 系统边界与技术架构

系统分为四个相互独立的部分：

1. **响应式 PWA 前端**：材料录入、背景板展示、本地状态和用户确认；
2. **事项分析服务**：将脱敏材料转换为固定结构的背景板数据；
3. **知乎检索适配器**：只接收抽象后的“事项＋困境”查询，返回可追溯来源；
4. **安全代理层**：保存服务端凭据、限制接口调用、校验模型输出。

用户原始材料默认保存在浏览器本地数据库。在线分析只接收经过用户预览确认的内容。知乎 Access Secret 和模型凭据只存在于服务端环境，不进入网页代码、浏览器存储或公开仓库。

第一版不把知乎知识库作为产品持久层，也不依赖企业内部系统、通讯录或组织权限数据。

## 8. 数据流

```text
用户输入原始材料
→ 本地抽取与敏感信息提示
→ 用户预览并确认脱敏版本
→ 事项分析服务生成结构化对象
→ 前端校验并显示背景板
→ 用户按需触发知乎搜索
→ 抽象查询发送到知乎检索适配器
→ 外部结果作为线索加入背景板
→ 用户执行询问并加入新回复
→ 系统生成 Revision 变化清单
→ 用户确认后更新事项状态
```

## 9. 异常与降级处理

### 9.1 材料不足

当系统无法判断关键补全者时，不编造人物职责。界面说明缺少什么，并只向用户提出一个最关键的补充问题。

### 9.2 模型输出不完整

服务端校验结构化结果。缺少必填字段时自动进行一次修复；仍失败则保留用户材料并提示重新分析，不展示半完整结论。

### 9.3 知乎搜索无结果或额度不足

背景板核心分析仍然可用。“别人走过的路”显示暂时不可用，不影响关键补全者和下一步行动。系统不自动反复请求。

### 9.4 网络中断

用户输入和已有背景板继续保存在本地。在线分析按钮提示稍后重试，刷新页面不丢失尚未提交的材料。

### 9.5 敏感信息

检测到姓名、手机号、证件号码、详细单位或内部项目名称时，产品在发送前突出显示，并提供一键替换建议。用户必须看见本次将被外发的文本。

### 9.6 判断可能误伤他人

涉及“故意隐瞒”“推卸责任”“针对新人”等动机判断时，界面阻止其进入人物结论，改写为可观察事实和不确定性说明。

## 10. 评委演示设计

宿舍入住是唯一主演示案例，户口迁移只作为首页或结尾的扩展案例。

三分钟演示节奏：

1. 0–20 秒：说明“每个人都告诉你一点，但事情仍然办不成”；
2. 20–45 秒：打开宿舍预置案例，展示多人信息碎片；
3. 45–90 秒：生成背景板，拆出资格、房间、入园、钥匙和通知五种状态；
4. 90–130 秒：展示关键未知以及人力/住宿管理方为何是关键补全者；
5. 130–160 秒：复制包含完整背景和具体困惑的求助信息；
6. 160–180 秒：加入模拟回复，展示事项从“等待确认”变为“可以行动”。

演示中必须能够展开至少一条结论查看原始证据，并展示至少一条来自知乎的相似经历，从而证明“可追溯”与“知乎生态”不是文案概念。

## 11. 比赛版本范围

### P0：必须具备

- 响应式首页和 PWA 基础能力；
- 无登录的宿舍预置案例；
- 新建事项和粘贴文本；
- 敏感信息提醒与外发内容预览；
- 结构化背景板及证据回溯；
- 关键未知、权威方和关键补全者判断；
- 可编辑、可复制的下一步询问；
- 手动添加回复并展示状态变化；
- 用户主动触发的知乎相似经历搜索；
- 网络或接口失败时的可理解降级。

### P1：时间允许时加入

- 聊天截图上传、文字提取和用户纠错；
- 更完整的离线缓存和 PWA 安装提示；
- 户口迁移预置案例；
- 从已解决事项自动生成简化的个人背景地图；
- 更丰富的不同答复分支模拟。

### 明确不做

- 登录、账号体系和跨设备同步；
- 企业部署、企业知识库和组织通讯录接入；
- 多人协作、公开分享和权限系统；
- 自动读取微信、邮箱或办公软件；
- 自动替用户发送消息；
- 领导性格、同事人格和办公室政治分析；
- 语音文件导入；
- 完整的个人公司背景地图管理界面；
- 以知乎知识库作为持久化数据库。

## 12. 验收与测试

### 12.1 功能验收

- 评委可以不登录完成宿舍案例全流程；
- 刷新页面后，本地事项与未提交材料仍然存在；
- 每条事实、说法和推断都能查看来源或状态说明；
- 关键补全者卡包含对象、依据、置信度、权限边界和未知项；
- 询问文本包含背景、已有信息、具体困惑、求助理由和明确请求；
- 新回复加入后，用户可以看到变化清单再确认更新；
- 知乎搜索失败时，背景板主体仍可正常使用；
- 客户端代码和网络响应中不出现服务端密钥。

### 12.2 AI 输出评测

使用匿名化宿舍案例及后续整理的 10–20 个事项样本，人工标注人物、说法、证据、未知、冲突和关键补全者。至少评估：

- 事实与说法混淆次数；
- 无依据的人物职责编造次数；
- 关键未知识别正确率；
- 关键补全者选择及依据是否合理；
- 询问文本五要素完整率。

### 12.3 用户验证

邀请 3–5 位职场新人和 1–2 位 HR 或行政人员，对背景板和通用聊天 AI 的输出进行盲评：

- 新人是否更清楚下一步找谁、问什么；
- 接收者是否愿意回复生成的消息；
- 哪种输出更容易区分事实与推断；
- 用户是否理解并信任关键补全者的判断依据。

第一版重点观察重复询问次数、从卡住到可以行动的时间，以及跑空或返工次数。

## 13. 成功标准

产品通过第一版验证，需要同时满足：

1. 用户能准确说出当前真正缺少的信息；
2. 用户知道下一步找谁，并理解为什么这个人最可能补全信息；
3. 用户能生成一条对方容易理解、回答或转交的求助信息；
4. 新回复可以改变背景板状态，而不是开始一段互不关联的新对话；
5. 与通用聊天 AI 相比，背景板更少混淆事实和说法，也更少编造人物职责；
6. 评委可以通过公开链接在三分钟内看到完整价值闭环。
